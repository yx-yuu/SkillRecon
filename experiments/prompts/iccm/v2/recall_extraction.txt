## Output Requirements
Return a JSON object with a "clauses" array. Each clause must have:
- step_id: identifier for the documentation step this clause comes from
- capability: one of the taxonomy atoms listed above
- operator: "allowed" | "prohibited" | "unknown"
- target: the specific target of the capability (URL, path, command, service, etc.), or null
- constraint: any scope or condition limiting this capability, or null
- constraints: an array retaining ALL typed scope restrictions and execution conditions for this operation
- evidence_span: direct quote from the document supporting this clause
- confidence_note: brief note explaining why this is a policy clause for one of the observed behaviors

Extraction policy:
- Extract only clauses that directly govern one of the observed sensitive behaviors, or a specific target/resource tied to that behavior.
- Do not extract generic feature descriptions or bare command examples unless the same text explicitly says what is allowed, disallowed, required, or limited.
- If a block only shows how to run a command or what output looks like, return no clause from that block.
- If the text contains a scoped restriction such as "only", "must", "do not", "without", "cannot", or similar policy language, preserve that restriction in target/constraint.
- If the block defines a concrete endpoint, host, auth header, required environment variable, or mandatory command for one of the observed behaviors, treat that as policy-bearing operational authorization rather than discarding it as a mere example.

- Keep a permission and all its attached restrictions in ONE clause. An explicit broad resource target and a narrower additional scope are different fields: retain the broad target, and put the narrower literal path/domain pattern alone in constraint. Do not create a separate unrestricted permission from the same sentence, or rephrase a scoped grant as an invented prohibition.
- Preserve scope values in their typed form (e.g. a path glob alone), without explanatory words such as "workspace scope" in the value. Plain purpose/location descriptions are evidence, not additional constraints. Keep genuinely unresolved governing conditions verbatim.
- Explicit before/after references to numbered steps are joint execution-order obligations. They are recovered from the source steps separately; do not duplicate a pure step-order requirement as an event-local scope constraint. Preserve the underlying event grant and any independent local restriction.
- Use the Table 1 typed selectors and conditions, including opt_out_env:VARIABLE, account_active:ACCOUNT, no_auto_retry and separate_invocation. Read and quote the whole governing step; later restrictions also govern operations described earlier in that step. Do not emit an unrestricted duplicate from a partial quote.
- Infer no HTTP transport from a named product, NFT, heading, or feature alone. Extract only documentary evidence.
