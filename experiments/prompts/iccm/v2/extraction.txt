## Output Requirements
Return a JSON object with a "clauses" array. Each clause must have:
- step_id: identifier for the documentation step this clause comes from
- capability: one of the taxonomy atoms listed above
- operator: "allowed" | "prohibited" | "unknown"
- target: the specific target of the capability (URL, path, command, etc.), or null
- constraint: any scope or condition limiting this capability, or null
- constraints: an array retaining ALL typed scope restrictions and execution conditions for this operation
- evidence_span: direct quote from the document supporting this clause
- confidence_note: brief note on extraction confidence

Extract ALL clauses you can find. Include both explicit declarations (like allowed-tools) and implicit capability references.

Important extraction guidance:
- A clause may be "allowed" even when the text uses operational requirement language instead of the words "allow" or "permit".
- Examples of operational authorization that should usually be extracted as "allowed":
  - "all requests require x-api-key header"
  - "set OURA_ACCESS_TOKEN before running"
  - "POST https://api.example.com/v1/..."
  - "run python scripts/main.py"
  - API parameter / endpoint tables that define the concrete request shape used by the skill
- Keep the target concrete when possible:
  - domain / URL / endpoint path for http_request
  - env var name for env_var_read or api_key_use
  - command / script name for shell_exec
  - request field or endpoint-specific limitation as constraint
- If the text is only a generic feature description with no concrete operational target or requirement, prefer "unknown".

- Keep a permission and all its attached restrictions in ONE clause. An explicit broad resource target and a narrower additional scope are different fields: retain the broad target, and put the narrower literal path/domain pattern alone in constraint. Do not create a separate unrestricted permission from the same sentence, or rephrase a scoped grant as an invented prohibition.
- Preserve scope values in their typed form (e.g. a path glob alone), without explanatory words such as "workspace scope" in the value. Plain purpose/location descriptions are evidence, not additional constraints. Keep genuinely unresolved governing conditions verbatim.
- Explicit before/after references to numbered steps are joint execution-order obligations. They are recovered from the source steps separately; do not duplicate a pure step-order requirement as an event-local scope constraint. Preserve the underlying event grant and any independent local restriction.
- Use the scope vocabulary: path:, prefix:, ext:, read_only, host:, domain:, scheme:, port:, opt_out_env:, var:, provenance:, account_active:, cmd:, interpreter:, arg_pattern:, no_auto_retry, location:, trigger:, lifetime:, source_class:, sink_domain:, separate_invocation. For example, if setting a named environment variable empty disables an operation, retain opt_out_env:VARIABLE on the operation's allowed clause.
- Read the whole step before emitting any clause. An operation described early in a step is still governed by the restrictions later in that step. Quote the complete governing text including those restrictions. Do not emit a shorter unrestricted duplicate grant from the same operation description.
- A named product, NFT, heading, or feature alone is not an HTTP capability indicator. Do not infer a transport or invent a resource from background knowledge.
